先读取 `emu/docs/architecture.md`，并使用当前仓库已经固化的工具链、依赖和 support 环境，基于 `Vortex_rtl` 完成 **T1：完整 ISA 单指令功能语义**。

本阶段目标是完整实现冻结配置实际启用的 ISA，使给定一条合法 32-bit 指令及其所需输入状态时，可以得到确定、可验证的架构可见结果；当前仍不实现完整 State、连续程序执行、Warp/SIMT 执行器、调度、CTA 或 Kernel execution。

主要完成：

1. 从冻结配置和 RTL 重新确认当前实际启用的完整 ISA 范围，建立统一的 ISA catalog/manifest。不得根据经验补充未启用指令，也不得直接把旧实验结果当作依据。

2. 实现完整、严格的 32-bit instruction decode。每个 enabled 指令应能够唯一解码，disabled、reserved 或非法编码必须确定性拒绝。

3. 实现冻结配置下全部单指令功能语义，包括实际启用的：

   * RV32I；
   * RV32M；
   * RV32F；
   * Zicond；
   * CSR/System；
   * fence/ordering；
   * Vortex custom/SIMT 指令。

4. ISA 层只负责单指令语义，不建立未来模拟器的长期 canonical State。根据 `architecture.md` 中已经确定的职责边界，通过抽象输入和结果/effect 与后续 State 层连接；具体接口形式可以在本阶段根据实际 ISA 需求逐步形成，不要为了测试方便提前固定不必要的 State 架构。

5. 对 load/store、CSR、控制流、浮点、cross-lane、warp control、barrier 等指令，表达其单指令架构可见行为即可。WSPAWN、WSYNC、BAR 等需要后续 Warp/Core/CTA 协作的指令，本阶段只完成 ISA 层能够确定的语义和输出边界，不实现真正的调度、同步或状态管理。

6. 直接复用当前实验区已经准备好的基础支持，例如 `support/softfloat`、`support/memory` 等；不要重新实现已有基础能力，也不要重新配置 Go 工具链和第三方环境。若确实需要新增依赖，按照现有环境和依赖管理规则处理。

7. 为每个 frozen-enabled 指令建立对应的 decode 和 functional test，并覆盖必要的边界情况。维护简洁的 ISA manifest/coverage 记录，使冻结 ISA 集合、decode、实现和测试能够逐项核对。

8. 整个 T1 过程中持续维护 `docs/architecture.md`。开始前读取现有 Contract；实现发现新的架构问题时加入 `UNRESOLVED`，解决已有问题时更新状态，实际实现验证或推翻 `PROVISIONAL` 设计时同步修改。不得为了符合旧文档而保留与 RTL 或实现不一致的设计，也不得只修改代码而留下过时的 Contract。

本阶段不实现：

* canonical Lane/Warp/CTA/Core State；
* instruction fetch loop 或连续程序执行；
* Warp.Step；
* 真正的多 lane/SIMT Warp 执行模型；
* Warp scheduler；
* barrier coordinator；
* CTA execution；
* Kernel loader/executor；
* cache、MMU、流水线、周期或性能模型。

T1 完成时应达到：

* 冻结配置下 enabled ISA 已完整确认；
* enabled 指令全部具有严格 decode 和单指令功能语义；
* 非法/disabled encoding 能够确定性拒绝；
* ISA 与未来 State/执行层之间的职责边界已经通过实际实现得到验证；
* ISA catalog、实现和测试完整对应；
* `docs/architecture.md` 已根据 T1 的实际发现同步更新；
* 使用项目现有 `scripts/verify.sh` 完成全量验证并通过。

不得修改 `Vortex_rtl`。
