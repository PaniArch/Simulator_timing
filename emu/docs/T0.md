基于 `/hpc2hdd/home/zekaiwang/vortex-work/Vortex_rtl`，为后续 Vortex 功能模拟器开发建立 `/hpc2hdd/home/zekaiwang/vortex-work/Simulator_v0/docs/architecture.md`，作为整个开发周期持续维护的 **Living Architecture Contract**。

最终目标是在冻结配置下输入 Kernel、入口和数据，完成功能执行并得到与 RTL/reference checker 一致的结果。本阶段只进行架构分析和 Contract 建立，不实现模拟器功能代码。

首先读取冻结配置和相关 RTL，确认当前功能模拟器实际需要支持的硬件配置和 ISA 范围，不根据经验补充配置中未启用的能力。

Architecture Contract 需要完成以下内容：

1. 梳理完整功能模拟器需要包含的主要层级和模块，明确各层的职责、上下级关系和依赖方向。

2. 梳理所有会跨指令持续存在的架构状态，明确每类 State 的 ownership，避免同一状态在不同模块重复维护。

3. 定义 ISA 层在完整模拟器中的职责边界，包括 ISA 需要读取什么、产生什么结果，以及与后续 State 和执行层之间应维护什么抽象接口。当前只确定接口职责，不提前固定具体实现形式。

4. 梳理不同类型指令可能影响哪些架构状态或上层模块，为后续 ISA、State、Warp、SIMT、Core、CTA 等阶段预留清晰的 effect/control 边界。

5. 描述从取指到单条指令产生架构可见结果的总体功能执行流程，以及各层在该流程中的职责。

6. 识别后续实现完整模拟器所需要的主要公共接口和模块边界，只记录用途、输入输出和依赖关系，不提前实现或固定具体 Go 类型。

7. 对影响后续架构设计的重要 RTL 语义进行必要调查。能够从当前 RTL 唯一确认的结论记录依据；不能确认的问题记录为 `UNRESOLVED`，说明问题本身以及最晚需要在哪个后续阶段解决，不在 T0 中强行猜测。

8. 明确当前功能模拟器的范围与非目标，区分架构功能语义和不需要模拟的微架构/性能行为。

`docs/architecture.md` 必须区分：

* `FROZEN`：已有充分依据、后续实现需要遵守的稳定契约；
* `PROVISIONAL`：当前设计方向，后续实现可以验证和修改；
* `UNRESOLVED`：当前证据不足、禁止猜测的问题；
* `RESOLVED`：后续阶段已经闭合的问题。

该文档不是 T0 的一次性交付。后续每个 Task 都必须先读取 Architecture Contract，并在实现结束后根据新的 RTL 证据和实际实现结果同步维护：新问题加入 `UNRESOLVED`，已解决问题更新状态，接口或 State ownership 发生变化时同步修改 Contract。不得只修改代码而留下过时的架构文档。

T0 不要求提前完成后续阶段的详细设计，也不要为了让文档看起来完整而提前确定尚未验证的 State 数据结构、具体接口、transaction/rollback 机制、调度算法、Kernel ABI 或其他实现方案。

本阶段最终只交付 `docs/architecture.md` 及确有必要的少量辅助架构文档，不实现 ISA、State、Warp、SIMT、scheduler、CTA 或 Kernel execution 代码，不修改 `Vortex_rtl`。
