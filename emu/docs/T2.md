先读取并遵守现有 `docs/architecture.md`，检查 T1 已完成的 ISA catalog、语义接口和测试，在此基础上完成 **T2：Architectural State**。

本阶段目标是建立模拟器真实、跨指令持续存在的架构状态，并把 T1 的 ISA 输入/输出接口连接到这些真实 State。完成后，ISA 不再只能依赖单元测试中的临时 fixture，而能够通过统一的 View / Effect 边界读取和修改模拟器真实状态。

当前仍不实现连续程序执行、`Warp.Step()`、scheduler、CTA 或 Kernel execution。

主要完成以下内容：

1. **根据 Architecture Contract 落地真实 State**

   依据 `docs/architecture.md` 中已经确认的 State ownership，实现当前阶段需要的长期架构状态。

   重点至少包括：

   * Lane 级长期状态，如整数寄存器、浮点寄存器及 T1 已确认属于 Lane 的其它状态；
   * Warp 级长期状态，如 PC、active mask、divergence/reconvergence state 及 T1 已确认属于 Warp 的其它状态。

   具体 State 字段和数据结构应根据当前 Contract、RTL 和 T1 实际接口决定，不直接沿用旧实验区设计，也不要为了后续阶段提前加入当前不需要的状态。

2. **保证 canonical ownership**

   每个架构状态只能存在一个长期真实 owner。

   ISA、View、Effect、测试 helper 或后续 executor 都不得维护另一份会独立变化的真实状态。

   对需要跨层引用的信息，应使用 ID、handle、只读 View 或其它不会形成重复 ownership 的方式。

3. **实现 State View**

   为 T1 ISA 提供读取真实 State 所需的统一只读接口/View。

   ISA 应能够通过这些 View 获得执行一条指令所需的信息，但不得获得能够绕过 State owner 直接修改长期状态的可变引用。

   View 的具体形式根据 T1 已形成的接口进行实现和必要调整，不在 Task 中预先规定固定 Go 类型。

4. **连接 T1 Architectural Result / Effect**

   建立 T1 ISA result/effect 到真实 State 的落地路径。

   至少能够正确处理当前属于 Lane/Warp 范围内的 effect，例如：

   * integer / FP register write；
   * PC update；
   * active mask update；
   * divergence/reconvergence update；
   * 已确认属于当前 State 层的 CSR 或其它架构状态更新。

   对明确属于后续 Core、CTA、Barrier Coordinator 等层级的 effect，不在 T2 越界实现其完整行为，只保证它们能够被识别并继续向未来 owner 传递。

5. **建立一致的提交与失败边界**

   一条 ISA effect 在真正修改 canonical State 前，应完成必要校验。

   如果 effect 无效或应用失败，不得留下寄存器已更新而 PC/mask/其它相关状态未更新的部分结果。

   根据当前实现选择简单、可靠的 commit/rollback 或 staged update 机制即可，不要求为了 T2 构建复杂 transaction framework、版本系统或并发控制。

6. **处理 x0、inactive lane 等基础状态规则**

   将 T1 已经确认的长期架构不变量真正落实到 State 层，并建立测试。

   例如寄存器特殊规则、合法索引、active mask 与 lane state 的关系等，应以当前 Architecture Contract 和 RTL 结论为准，而不是重新在 ISA handler 中维护。

7. **为后续 CoreState / CTAState 保留边界**

   根据 Architecture Contract，为后续 Multi-Warp Core 和 CTA 阶段保留必要的引用和接口边界。

   当前不要求实现完整：

   * CoreState；
   * WarpManager / Scheduler；
   * CTAState；
   * BarrierCoordinator；
   * WSPAWN 的真实 Warp 创建；
   * BAR 的真实跨 Warp 同步。

   只保证当前 State 设计不会要求这些未来模块复制 Lane/Warp 的 canonical state。

8. **验证 ISA → State 连接**

   建立定向测试，证明 T1 的 ISA semantic 可以通过真实 State View 执行，并通过 effect 正确修改 canonical State。

   测试应覆盖不同类型的代表性语义，例如：

   * integer register result；
   * FP register / flags；
   * PC/control result；
   * active mask；
   * divergence state；
   * 必要的 CSR state；
   * effect 失败时 State 保持一致；
   * 不属于当前 owner 的 effect 不被错误消费。

   不需要在 T2 再为全部 ISA 复制一套逐指令测试；T1 的 ISA semantic 测试继续负责指令正确性，T2 重点验证 State integration 和 ownership。

9. **持续维护 Architecture Contract**

   T2 开始前读取 `docs/architecture.md`。

   实现过程中重点验证 T0/T1 中关于：

   * State ownership；
   * ISA 与 State 边界；
   * View；
   * effect ownership；
   * commit 边界；

   的 `PROVISIONAL` 设计。

   如果实际 State 实现证明某项设计需要修改，应同步更新 Contract；新发现的问题加入 `UNRESOLVED`，已闭合问题更新为 `RESOLVED`，有充分依据的稳定结论可以升级为 `FROZEN`。

   不得为了符合旧 Contract 而维护明显不合理的 State 结构，也不得只修改代码而不更新 Contract。

10. **复用现有实验环境**

继续使用 `Simulator_T2` 已固化的 Go 工具链、依赖和 support packages。

不重新配置环境，不重复实现现有基础 support，也不得修改 `Vortex_rtl`。

## 本阶段不实现

* instruction fetch loop；
* 连续 instruction stream；
* `Warp.Step()`；
* single-lane program execution；
* 完整 SIMT Warp 执行循环；
* Multi-Warp scheduler；
* WSPAWN 的真实 Warp 创建和调度；
* barrier completion；
* CTA execution；
* Kernel execution；
* cache/MMU/pipeline/周期或性能模型。

这些属于 T3 及后续阶段。

## T2 完成标准

T2 完成时应达到：

* Lane/Warp 范围内需要长期保存的架构状态已有真实 canonical State；
* 每类 State ownership 清晰，没有重复长期状态；
* T1 ISA 可以通过真实 State View 获取所需输入；
* T1 的 Lane/Warp 范围 effect 可以正确提交到真实 State；
* 跨 Core/CTA 的 effect 保持清晰边界，没有被 T2 越界实现；
* effect 失败不会留下 partial State update；
* State integration 的定向测试完整通过；
* T1 原有 ISA 全量测试保持通过；
* `docs/architecture.md` 已根据 T2 实际实现同步维护；
* 使用项目现有 `scripts/verify.sh` 完成全量验证并通过。

T2 的最终交付是 **可以被后续执行器长期持有和修改的真实 Architectural State 层**；下一阶段 T3 才在其上加入 instruction fetch、PC 推进和 Single-Lane Warp 连续执行。
