先读取并遵守现有 `docs/architecture.md`，检查 T1 已完成的 ISA semantic layer 与 T2 已完成的 Architectural State，在此基础上完成 **T3：Single-Lane Warp Executor**。

本阶段目标是第一次建立真正的**连续执行模型**：让一个 Warp 在只有一个 active lane 的情况下，从给定入口 PC 开始反复执行 `fetch → decode → ISA evaluate → effect commit → next PC`，能够运行简单 instruction stream，而不再只能执行孤立的一条指令。

当前阶段不实现真正的多 lane SIMT、divergence、多 Warp 调度、CTA 或 Kernel execution。

## 1. 建立 Single-Lane Warp 执行模式

基于 T2 的真实 `WarpState` / `LaneState`，建立一个最小可运行 Warp：

* 一个 Warp；
* 只有一个 active lane；
* 使用真实 Warp PC；
* 使用真实 Lane GPR/FPR；
* ISA 继续复用 T1 的 decode/evaluate；
* State 更新继续通过 T2 的 View / Effect / commit 边界完成。

Single-Lane 模式的目的不是建立另一套 State，而是用现有真实 State 运行最简单的执行循环。

## 2. Instruction Fetch

实现 Warp 基于当前 PC 获取下一条指令的功能。

Instruction fetch 应通过现有 Architecture Contract 中定义的 InstructionSource / memory 边界完成，不应让 Warp 自己维护第二份 program bytes。

至少处理：

* 当前 PC；
* 32-bit instruction fetch；
* little-endian instruction bytes；
* 地址范围和对齐错误；
* fetch failure / invalid access；
* 返回 raw instruction bits。

当前冻结配置若不支持 compressed instruction，则不需要实现 16-bit fetch。

不实现 I-cache timing、miss、prefetch 或其它微架构行为。

## 3. Warp.Step()

实现本阶段的核心入口：

```text
Warp.Step()
```

一轮 Step 应完成：

```text
读取当前 Warp PC
        ↓
Instruction Fetch
        ↓
ISA Decode
        ↓
构建当前 lane/warp 所需 State View
        ↓
ISA Evaluate
        ↓
得到 Architectural Result / Effect
        ↓
Validate / Resolve
        ↓
Commit 到 T2 canonical State
        ↓
得到新的 Warp PC / execution outcome
```

`Warp.Step()` 不应重新实现任何 ISA semantic。

ISA decode 和单指令语义必须复用 T1；状态读写和 commit 必须复用 T2。

## 4. PC 更新与控制流

建立连续执行所需的 PC 推进规则。

至少支持：

* 普通 fallthrough；
* branch；
* JAL；
* JALR；
* trap/control flow 中 T1/T2 已支持的 PC effect；
* fetch/decode/evaluate fault 时的确定性结果。

PC 只能通过已经确认的 canonical owner 更新，不得在 WarpExecutor 中维护另一份长期 PC。

需要保证一次成功的 Step 只产生一个最终 PC 结论。

如果 T1/T2 中关于控制流的 `PROVISIONAL` 设计在连续执行后暴露问题，应在本阶段修正并同步更新 Architecture Contract。

## 5. Single-Lane Effect 执行

本阶段只运行一个 active lane，因此普通 lane-scope instruction 只对该 lane evaluate 和 commit。

需要能够连续执行至少包括：

* integer arithmetic；
* RV32M/Zicond；
* branch/jump；
* load/store；
* FP；
* CSR/System；
* 其它不依赖真正多 lane 协同的已实现指令。

对于需要完整 Warp、多 lane、Core 或 CTA 上下文才能正确执行的指令，不要在 T3 伪造真实 SIMT 行为。

根据现有 T1 effect 分类：

* 能在 single-lane 条件下有确定语义的，可以执行；
* 必须依赖后续 SIMT/Core/CTA 的，应返回明确的 unsupported/deferred execution outcome 或按照现有 Contract 规定的方式停止执行；
* 不得为了让程序继续跑而自行猜测跨层行为。

## 6. Memory 连续执行连接

将 T1 的 memory intent 和 T2 的 State commit 接入真实连续执行。

至少保证：

* load 能从当前 memory backing store 读取并写回 lane state；
* store 能正确修改 memory；
* load/store failure 不留下 partial register/PC update；
* instruction fetch 与 data access 维持 Architecture Contract 中确认的 memory ownership；
* 使用当前 support/memory 提供的基础机制，但不把 support package 本身等同于未来完整 memory architecture。

本阶段不实现 cache、coalescing、MMU 或 memory timing。

## 7. 简单连续 instruction stream

在 `Warp.Step()` 基础上提供一个最小连续执行入口，例如：

```text
Run / RunUntil / ExecuteSteps
```

具体 API 根据现有架构设计决定，不提前固定名称。

应能够：

* 从入口 PC 开始；
* 重复调用 Step；
* 在每一步 commit 后使用新的 PC；
* 在明确 completion、fault、unsupported instruction 或 execution budget 达到时停止；
* 返回确定性的 execution outcome。

必须提供 instruction/step budget，避免 PC 或控制流 bug 导致无限执行只能靠外部 timeout 结束。

## 8. Execution Outcome

建立本阶段需要的最小执行结果分类，使后续 T4–T7 可以继续扩展。

至少能够区分：

* instruction retired / progress；
* fault / trap；
* unsupported later-stage effect；
* execution budget exceeded；
* program/warp finished（如果当前 RTL/Contract 已有明确 single-lane completion 语义）。

具体枚举和结构根据现有 Architecture Contract 决定。

不要在 T3 提前设计完整 Multi-Warp scheduler 状态机。

## 9. Trace / Logging

接入当前实验区已有 logging 基础能力，为连续执行提供最小可观察 trace。

至少能够在需要时记录：

* step；
* Warp ID；
* PC；
* raw instruction；
* decoded instruction；
* relevant effect；
* next PC；
* execution outcome。

默认运行不应产生过量日志；trace 应可开关。

本阶段 trace 只服务于 correctness/debug，不模拟 pipeline trace。

## 10. 测试要求

T3 的重点是验证**连续执行链路**，不是重新复制 T1 的全部单指令测试。

建立小型 instruction stream / program tests，至少覆盖：

* 多条顺序 integer instruction；
* register dependency；
* branch taken / not taken；
* loop；
* JAL/JALR；
* load/store 后续依赖；
* FP 指令参与连续执行；
* CSR/control 指令在当前支持范围内的连续行为；
* fetch fault；
* illegal instruction；
* memory fault；
* effect failure 不产生 partial state；
* execution budget 能终止错误循环。

测试应检查执行后的真实：

* PC；
* GPR/FPR；
* memory；
* 必要 CSR；
* execution outcome。

如果已有 ELF/support 能方便构造测试输入，可以使用，但当前不要求建立 Kernel/ELF program execution pipeline；简单的 instruction memory / hand-built instruction stream 足够完成 T3 验证。

## 11. 不处理真正 SIMT

本阶段固定为 single active lane。

不实现：

* 多 active lanes 同时执行；
* lane effect aggregation；
* TMC/PRED 的真实多 lane mask 行为；
* SPLIT/JOIN divergence execution；
* VOTE/SHFL/WGATHER 的真实 cross-lane execution；
* 多 Warp；
* WSPAWN 的真实 Warp 创建；
* WSYNC 的跨执行协调；
* barrier completion。

这些属于 T4 及以后阶段。

## 12. 持续维护 Architecture Contract

T3 开始前必须读取 `docs/architecture.md`。

本阶段重点验证此前关于：

* Warp PC ownership；
* ISA → State effect flow；
* InstructionSource；
* memory access boundary；
* control-flow result；
* WarpExecutor 职责；
* completion/outcome；

的 `PROVISIONAL` 设计。

连续执行过程中如果发现某些接口或 ownership 不适合真实 `Warp.Step()`，应根据 RTL 和实现结果调整并同步更新 Contract。

新问题加入 `UNRESOLVED`；解决的问题更新为 `RESOLVED`；只有具有充分证据且经过当前实现验证的稳定结论才升级为 `FROZEN`。

不得为了兼容旧接口而保留明显错误设计，也不得只修改代码而留下过时的 `architecture.md`。

## 13. 环境与范围约束

继续复用 `Simulator_dev` 已固化的工具链、依赖和 support packages。

不得：

* 重新配置 Go/toolchain；
* 重写 T1 ISA semantic；
* 重建 T2 State；
* 修改 `Vortex_rtl`；
* 开始 Multi-Warp、CTA 或 Kernel 实现；
* 引入 cache/MMU/pipeline/cycle/performance 模型。

## T3 完成标准

T3 完成时应达到：

1. 一个真实 `WarpState` 可以从入口 PC 开始执行；
2. Instruction fetch 能稳定获得下一条 32-bit 指令；
3. `Warp.Step()` 完成 fetch → decode → evaluate → commit → next PC 的完整链路；
4. T1 ISA semantic 和 T2 State 被直接复用，没有重新实现第二套逻辑；
5. 普通 single-lane integer、FP、memory、branch/jump、CSR 等指令可以连续执行；
6. 可以运行简单 instruction stream，而不只是单指令测试；
7. fetch/decode/memory/effect failure 不产生错误的 partial state；
8. 有明确 execution outcome 和 step budget；
9. 连续执行相关测试和原 T1/T2 回归全部通过；
10. `docs/architecture.md` 已根据真实 WarpExecutor 实现同步维护；
11. 使用项目已有 `scripts/verify.sh` 完成全量验证并通过。

T3 最终交付的是 **一个能够连续执行程序的 single-lane Warp functional executor**。下一阶段 T4 才把这个执行模型扩展到完整 4-lane SIMT Warp。
