# Task 12：L1 Memory System 与完整周期模拟器闭合

在 Task11 已完成的 Multi-Warp Core、CTA/Kernel 执行闭环基础上，以冻结 RTL 和 Timing IR 为主要依据，补齐 Core 到外部 memory 之间的存储层级，完成当前冻结配置下周期模拟器的完整构建。

本阶段重点是实现 L1 级存储行为、访存请求组织和真实的存储资源竞争，使 Fetch、LSU、LMEM 与 Kernel execution 不再依赖简单的固定延迟 memory service。

## 主要内容

建立冻结配置下的完整访存路径：

```text
Fetch
  ↓
L1 I-Cache
  ↓
External Memory Backend

LSU
  ↓
Local / Global 路由
  ├─ Local Memory
  └─ Memory Coalescing
        ↓
      L1 D-Cache
        ↓
External Memory Backend
```

根据 RTL 实现当前配置实际启用的 I-cache、D-cache 和 local memory 行为。

L1 Cache 应表达命中与缺失路径、bank/port 资源、请求队列、MSHR、replacement、refill、store/update、writeback 及相应 backpressure，使 Cache 状态和资源占用真实影响 Fetch 与 LSU 推进。容量、路数、延迟及结构参数从冻结配置和 RTL 获取，不另建经验参数表。

实现 SIMD lane 访存请求的组织、合并和返回拆分，根据 RTL 确定地址分组、byte enable、请求覆盖、response mask、tag 和资源冲突关系。区分 lane 访问粒度、合并输出粒度、Cache bank 粒度和 Cache line/refill 粒度，不将同一 Cache line 内的访问默认视为一次请求。

Local memory 保留既有地址和数据功能语义，并补充 RTL 中实际存在的 local/global 路由、bank、端口、冲突和响应时序，使 LMEM 与 global memory 分别经过对应的周期路径。

## 访存衔接与数据可见性

将当前直接访问 backing memory 的抽象服务替换为真实的 Cache/LMEM 请求与返回路径。

功能层继续产生地址、byte enable、store data 和 load completion 语义；周期存储系统负责请求如何拆分或合并、何时接受、经过哪些资源以及何时返回数据。Load completion 必须使用存储系统实际返回的数据，不能在 Cache 响应后再次绕过 Cache 读取 backing memory。

允许根据真实存储路径调整现有 Runner、effects 和 memory 接口，不强制保留 Task11 中整组 lane 一次 `WriteBatch` 的服务方式。

对于 SIMD store，应依据 RTL 处理同址和字节重叠请求。能够由访存合并规则确定的数据应按对应 byte enable 合并；无法从 RTL 静态确定的跨组冲突顺序不得通过 Go 遍历顺序自行规定。

Mixed local/global lane 请求需要保持两条子路径的接受关系和 response identity，在其中一路背压时不能重复提交另一部分，也不能提前认为整条 LSU 请求已经完成。

Cache 数据、dirty line 与 external backing memory 之间应有明确的可见性关系。在采用 writeback Cache 时，store 不得继续无条件立即修改 backing memory。

## 存储顺序与同步

加入 Cache hit/miss、bank conflict、refill 和不同响应延迟后，依据 RTL 维护同址读写、未完成 miss、后续请求和 memory response 之间的顺序关系，不以预设完成周期或软件遍历顺序代替硬件规则。

继续区分：

* hardware instruction pending；
* LSU scheduler drained；
* Cache / memory system outstanding work；
* software effect completion；
* backing memory visibility。

BAR、WSYNC、FENCE、Cache flush 和 Kernel completion 分别使用其对应的硬件条件，不统一解释为“整个存储系统全部排空”。

FENCE、I/D-cache flush 等冻结配置实际使用的控制路径应进入新的存储系统，不继续作为空操作直接完成，也不得通过强制整个 Core 串行排空来规避正确的 memory ordering。

## 外部 Memory 边界

L1 之外不实现真实 DRAM 微架构。

建立简单、确定的 external memory backend，为 I-cache/D-cache miss、refill 和必要的 writeback 提供请求与响应。例如：

```text
External Memory Latency = 100 cycles
```

该延迟只表示 L1 以下未建模存储系统的统一服务时间，不模拟 DRAM channel、bank、row buffer、controller 或调度策略。

固定延迟从 external backend **实际接受请求**开始计算，而不是从指令 Issue 或 Cache miss 检测开始。

同时明确最小的请求接受能力、在途数量和返回带宽，使多个 miss 能产生合理的竞争和 backpressure。该层保持简单确定，不扩展为 DRAM 模拟器。

接入新的存储路径后，不再叠加原有 `FetchCycles` / `MemoryCycles` 作为整条访问路径的统一延迟；L1 hit、LMEM、Cache miss 和 external memory 应分别由对应组件决定周期。

## Kernel 与资源生命周期

将 Task11 Kernel execution 接入新的 I-cache、D-cache、LMEM 和访存合并路径，使完整 Kernel 的 instruction fetch、global load/store 和 local memory 都经过周期存储系统。

CTA/Warp slot 回收需要考虑仍可能使用该 residency 信息的请求、合并状态、Cache/LMEM response 和其它有效 token，防止旧 CTA 的迟到事件污染复用后的资源；同时不要求无关 CTA 或整个 Core 排空。

区分：

```text
Warp 停止取指
CTA 可回收
Kernel 执行结束
存储请求排空
最终输出对 backing memory 可见
```

这些状态不能简单合并。

Cache 中存在有效 line 或 dirty line 本身不等于仍有执行中的 memory request。若最终结果需要从 backing memory 读取，则应通过明确的写回或可见性操作保证结果已经可观察，不通过直接复制 Cache 数据或无条件清空 Cache 绕过一致性关系。

## Timing IR 维护

实现过程中持续核对冻结 RTL 中：

* local/global memory split；
* memory coalescer；
* LSU adapter；
* LMEM；
* I-cache / D-cache；
* cache bank；
* MSHR；
* replacement；
* refill / writeback；
* request / response buffer；
* flush 与 empty/busy 条件。

发现现有 Timing IR 的参数、边界或规则不足时，同步更新 Markdown 与 YAML，并保留 RTL evidence。

能够确认的行为写入结构化 Timing IR；不能静态确认的冲突顺序、同时事件或后端行为继续标记为 `UNRESOLVED`，不通过实现方便性自行补定。

## 约束边界

本阶段不实现：

* DRAM controller 及 DRAM 内部时序；
* L2 / L3 Cache；
* 多 Core Cache coherence；
* VM / TLB / page-table timing；
* host runtime；
* RTLSIM trace 精度收敛。

保留 Task9–Task11 已完成的 Scheduler、Scoreboard、执行流水和 Kernel orchestration 主体，但允许为真实存储路径调整访存接口、控制衔接和完成判断。

若 memory backpressure 暴露已有周期控制错误，应根据 RTL 修正对应接口和 Timing IR，而不是增加旁路、全局 drain 或额外串行限制。

CTA dispatcher 的逐 Warp 内部 pipeline、Barrier RAM 内部时序等 T11 已明确保留的抽象不要求在本阶段强行补齐，但应继续明确记录，不能因 T12 完成而默认已经达到 RTL 周期等价。

## 验证重点

除原有 Kernel 回归外，至少覆盖：

* Cache hit / miss 与连续访问；
* MSHR 满和释放后的恢复；
* dirty replacement 与 writeback；
* I-cache miss 对 Fetch 的阻塞；
* D-cache bank / port 竞争；
* store 后 load 的数据可见性；
* SIMD lane 访存合并与 response 拆分；
* 同址同值及 byte-overlap store；
* mixed local/global 请求及不对称 backpressure；
* LMEM bank conflict；
* Barrier + LMEM 的多 Warp 协作；
* CTA 复用时仍存在 memory tail 的情况；
* Kernel 结束和最终输出可见性。

改变 external memory latency、Cache miss pattern 和请求 backpressure 后，程序最终架构状态和输出仍应保持正确。

## 完成标准

完成后，周期模拟器能够使用 Task11 的 Kernel 入口执行完整 Kernel，并实际经过：

```text
Multi-Warp Pipeline
        ↓
Fetch / LSU
        ↓
Local-Global Routing
        ↓
Coalescing / LMEM
        ↓
L1 I-Cache / D-Cache
        ↓
Fixed-Latency External Memory Backend
```

Cache hit、miss、MSHR、访存合并、bank/port 冲突、LMEM 冲突、refill、writeback 和 external memory latency 均能够影响实际执行周期与 Warp stall。

存储系统不存在通过旧固定延迟 service、直接 backing-memory 访问或全局串行 drain 绕过真实资源关系的路径。

在不同 Cache 行为、访存竞争和 external memory 延迟下，完整 Kernel 能正确执行、正确回收 CTA，并产生正确的最终输出。

Task12 最终交付的是 **冻结单 Core 配置下功能执行链、Multi-Warp/CTA/Kernel 控制链以及 L1/LMEM 存储层级均已闭合的周期级 Vortex 模拟器**。

Task12 之后不再继续扩展基础模型结构。write
