# Task 11：周期控制完善与 Kernel 执行闭合

以仓库内 `Vortex_rtl/` 冻结配置和 RTL 源码为核心依据，结合现有 Timing IR 与 Multi-Warp 周期实现，修正影响正常执行的控制边界，建立从 Kernel launch 到全部工作完成的周期执行闭环。

## 主要内容

### 周期控制完善

区分硬件指令 pending、LSU 排空、软件效果交付和外部访存完成，不再用同一组软件记录代替不同硬件条件。根据 RTL 明确 WSYNC、BAR、WSPAWN 的等待、状态更新与唤醒关系，避免因既有接口限制引入额外串行化。

补齐架构可读计数器、active Warp 等状态的周期来源，区分宏指令、uop 和实际提交事件。审查现有 `UNRESOLVED` 与拒绝执行条件，补齐正常可达路径中的反馈合并、CSR 背压和控制优先级；不将正常 Kernel 可能触发的停止条件仅作为精度问题遗留。

### Kernel 执行闭环

建立与 host runtime 解耦的 Kernel 级入口，接收硬件可见 launch state，以及已经装载程序、参数和数据的 memory。

根据 RTL 完成 Grid/CTA 生成、资源接纳、Warp 初始化、线程与 CTA 上下文、resident CTA 管理和资源回收。区分 startup PC、kernel entry 与参数地址，使工作通过现有周期 Core 实际执行，而不是在外层调用功能执行循环。

接通 Barrier 协调、SIMT 控制及 Warp 阻塞恢复，使多个 Warp 能通过 local memory 和同步操作协作，并在 CTA 结束后继续执行后续 CTA。

### 完成与回收

区分 Warp 停止取指、指令提交、访存完成、CTA 资源可回收和 Kernel 完成。避免仍有有效请求、反馈或效果等待时提前结束，也不默认要求每次 CTA 接纳或回收都排空整个 Core。

明确 slot 复用时的上下文与请求身份，防止上一 CTA 的迟到事件影响新工作。保留必要的周期事件与阻塞原因观测。

## 约束边界

已有 `emu/docs/architecture.md` 和功能模拟器作为辅助语义参考及结果对照。允许根据 RTL 与周期实现需要复用、适配或重新组织相关部分，**不强制保留既有包、状态组织、事务接口或 Step/Run 推进方式**。状态职责及可见事件应明确，不以迁就旧接口为理由改变硬件控制关系。

访存暂采用请求、响应和数据可见性明确的抽象服务，支持 Kernel 所需的 global/local memory 功能与同步；本阶段不实现 L1 Cache、LMEM bank 等存储内部时序，也不实现 DRAM、L2/L3、多 Core、host runtime 或 RTLSIM 精度收敛。不继续扩展与正常执行闭环无关的通用恢复机制。

实现过程中同步维护 Markdown 与 YAML Timing IR，区分 RTL 事实、软件抽象和未决事项，保持已有验证通过。

## 完成标准

能够从 launch state 启动完整 Kernel，执行多 Warp 协作及超过一次驻留容量的多个 CTA，正确完成同步、资源复用和最终输出；在明确的抽象访存延迟与背压下持续推进，不提前报告完成。**本阶段以正常 Kernel 执行能力和控制边界闭合为目标，不要求周期精度已经收敛。**
