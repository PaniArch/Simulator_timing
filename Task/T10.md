# Task 10：Multi-Warp Scheduling 与动态流水控制

先读取并遵守现有 Timing IR 和 Task9 周期流水线实现，在冻结 RTL 与已有功能语义基础上，将当前单活动 Warp 的周期执行框架扩展为冻结配置下真实的 Multi-Warp Core。

本阶段重点不是增加新的流水组件，而是建立 Warp 调度、数据相关和动态阻塞控制，使多个 Warp 和多条指令能够同时处于流水线不同位置，并按照资源、依赖和控制状态逐周期推进。

## 主要内容

在 Task9 已有 Fetch、Decode、IBuffer、Issue、Operand/Dispatch、Execution、Commit/Writeback 路径上加入完整的调度控制，包括：

* 冻结配置下 4 个 Warp 的 active、stalled、runnable 等周期状态；
* Warp Fetch 选择以及前端 PC、mask 和流水中 instruction identity 的关联；
* IBuffer 占用对 Fetch 调度的约束；
* Scoreboard 的寄存器与特殊状态依赖跟踪；
* Issue eligibility、FU credit 和共享资源可用性判断；
* 多 Warp Issue 仲裁与稳定的选择顺序；
* Writeback、Commit、branch、SIMT control 和执行完成产生的 release / wakeup；
* Warp pending work 和 drain 状态；
* 控制重定向后对年轻指令的失效和流水清理。

解除 Task9 的“当前指令完全排空后才允许下一条进入”限制，使多个 Warp、同一 Warp 的多条无依赖指令以及不同执行单元能够真实重叠执行。

## 功能语义与状态边界

继续使用已有 emu/docs/architecture.md 和架构状态作为功能结果与 canonical state 的基础，不在 timing 层复制指令、SIMT、CSR 或 memory 功能语义。

已有功能模拟器中的 Warp lifecycle、状态 ownership 和相关功能规则可作为参考和复用基础，但不得直接沿用其 `Core.Step`、round-robin 单步推进或“一次选择即完成整条指令”的执行关系。

周期层应根据真实流水事件决定 Warp 是否可 Fetch、Issue、阻塞或恢复；功能状态只在已经定义的可见事件发生时更新。

特别区分：

* Scheduler 使用的前端 PC / mask；
* 流水 Token 已锁存的 PC / mask；
* Functional owner 中最终架构可见的 PC / mask。

Branch、SPLIT/JOIN、TMC 等反馈不能通过重新读取最新 WarpState 替代流水中已经锁存的指令上下文。

## Timing IR 维护

实现过程中持续核对冻结 RTL 中 Scheduler、Issue、Scoreboard、Commit 和相关反馈路径。

若发现现有 Timing IR 对以下内容描述不足，应同步补充：

* Warp eligibility；
* scoreboard reserve / release；
* pending instruction；
* fetch / issue arbitration；
* IBuffer full 与调度关系；
* 同周期 writeback release；
* branch / SIMT stall 与 unlock；
* flush 和状态可见周期。

未能静态确认的同时事件和优先级继续保留为 `UNRESOLVED`，不通过软件调用顺序自行补定。

## 本阶段边界

本阶段不要求实现：

* CTA generation、admission 和 reclaim；
* 完整 Kernel execution；
* 多 CTA residency；
* L1 I-cache / D-cache；
* cache MSHR、replacement 和 refill；
* DRAM timing；
* 多 Core、多 Cluster；
* RTLSIM trace 精度收敛。

现有 memory service 可继续作为明确延迟的外部响应边界，用于验证 Scheduler 在长延迟 LSU 操作下的 Warp 切换与 latency hiding，但不能将该延迟视为最终 Cache 模型。

Barrier、WSPAWN、WSYNC 等已有功能和周期 effect 接口可保留并为后续阶段提供控制反馈边界；本阶段重点是保证 Scheduler 能正确处理 Warp 的阻塞、恢复和 pending 状态，不扩展到完整 CTA/Kernel orchestration。

## 完成标准

完成后应具备一个能够真实并发推进冻结配置下多个 Warp 的周期 Core：

* 4 个 Warp 能够独立 Fetch、阻塞、恢复和完成；
* 多条指令能够同时驻留于不同流水资源；
* 无依赖指令能够形成正常流水吞吐；
* 数据相关能够由 Scoreboard 正确阻止 Issue；
* Writeback 后依赖能够按照定义的周期重新变为可执行；
* 不同 Warp 能够在长延迟操作期间继续利用可用执行资源；
* IBuffer、Dispatch Queue、FU 和 Commit 等资源竞争能够影响实际调度；
* branch / SIMT 控制能够停止错误的后续推进并恢复到正确路径；
* Warp pending、stall reason 和 scheduler decision 可被 trace 观察；
* 最终架构结果与已有功能语义保持一致；
* Timing IR 与实际 Scheduler / Scoreboard 实现保持同步。

Task10 最终交付的是 **一个具备 Multi-Warp 调度、Scoreboard、资源仲裁和真实重叠流水能力的单 Core 周期执行模型**。

下一阶段在该 Core 上接入 CTA、Barrier、Warp residency 和 Kernel 生命周期，使周期模拟器能够从 Kernel launch 一直执行到完整 Kernel 结束。
