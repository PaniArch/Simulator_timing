# Task 9：周期流水线框架

先读取并遵守 Task8 形成的 Timing IR，在已有功能模拟器以及冻结 RTL 的基础上，构建周期级模拟器的第一版流水线执行框架。

本阶段目标不是实现完整的周期准确模型，而是将 Task8 中确认的流水结构、资源边界和时序关系落实为可运行的周期推进机制，使指令能够按照明确的流水阶段和资源路径逐周期向前推进。

## 主要内容

根据 Timing IR 建立冻结配置下的核心流水结构，覆盖 Fetch、Decode、Issue 前端、Operand/Dispatch、Execute、Commit/Writeback 等主要路径，并表达其中必要的 Buffer、Queue、Pipeline 和执行单元。

各流水组件应独立维护自身的容量、占用和在途状态，通过明确的接收、推进和完成边界进行交互，避免由上层直接修改其它组件内部状态。

建立统一的周期推进机制，保证对象按照真实注册边界跨周期移动，并能够表达：

* 有界缓冲和 backpressure；
* 固定或流水化执行延迟；
* 长延迟操作的等待与完成；
* 下游资源不可接受时的停留；
* flush、completion 等后续控制所需要的基本接口。

本阶段采用最小控制方式驱动流水线，只需要使单一活动 Warp 能够稳定经过完整流水路径，用于验证流水结构、周期推进和功能语义衔接。真实的多 Warp 选择、数据相关和资源仲裁留到下一阶段。

## Timing IR 维护

Task8的 Timing IR 不是不可修改的最终规格。

实现过程中如果发现：

* 原流水边界理解不准确；
* 缓冲、容量或 latency 与 RTL 不一致；
* 需要补充新的组件或交互关系；
* 原有设计假设不足以支撑实现；

应同步修正 Markdown 与 YAML 中对应的 Timing IR，并保留 RTL 证据或 `UNRESOLVED` 状态。

实现代码与 Timing IR 必须保持一致，不能只在代码中加入无法追溯的时序规则。

## 本阶段边界

本阶段不要求实现：

* 完整多 Warp Scheduler；
* Scoreboard 和完整数据相关控制；
* Warp 间资源仲裁策略；
* 完整 cache/MSHR/DRAM 时序模型；
* RTLSIM trace 对齐与周期精度修复；
* 多 Core、多 Cluster；
* host runtime 或外部 runtime adapter。

访存和其它长延迟路径可以建立能够支撑后续扩展的请求、等待和完成边界，但不在本阶段扩展为完整 memory hierarchy。

## 完成标准

完成后应具备一个可独立运行和观测的周期流水线框架：

* 指令能够通过主要流水组件逐周期推进；
* 流水级、缓冲容量和执行延迟实际影响推进过程；
* backpressure 能阻止对象错误前进；
* 同一对象不会在一个周期内错误击穿多个注册边界；
* 功能结果仍由已有 Functional IR 路径产生；
* 单一活动 Warp 能够经过完整流水路径持续执行；
* 各流水阶段的进入、停留、离开和完成周期能够被观察；
* Task8 Timing IR 与实际实现保持同步。

Task9 最终交付的是 **一个具备明确组件边界、周期推进、资源占用和功能语义衔接能力的基础周期流水线模型**。下一阶段在这一框架上加入真实的多 Warp Scheduler、Scoreboard、仲裁和动态阻塞控制。
