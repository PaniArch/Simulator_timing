# Task 8：初版 Timing IR

先阅读 `emu/docs/architecture.md`，理解已有 Functional IR 中的功能语义、状态所有权、effect 边界及待决问题；结合仓库中的功能模拟器实现和 `Vortex_rtl/` 冻结工程，建立面向后续周期模拟器的**初版静态 Timing IR**。

## 参考与职责区分

- **`Vortex_rtl/`**：用于确认当前配置下的流水结构、资源、连接关系和周期规则。
- **`emu/docs/architecture.md`**：用于理解功能结果、架构状态和已有语义边界，不将其中的功能执行顺序直接视为硬件时序。
- **现有功能模拟器及支撑代码**：评估可复用、需适配或需重新组织的部分，不预先指定必须沿用的包、类型和调用链。周期模型不必继承原有 Warp/Core/Device 的实现组织。

## 主要内容

围绕冻结配置下的实际执行路径，梳理流水阶段、注册边界、缓冲与队列、执行单元、端口及连接关系；记录能够从 RTL 确认的容量、执行延迟、吞吐率，以及基本传输、阻塞和完成条件。

识别调度、数据相关、资源仲裁、访存响应和控制反馈所涉及的时序边界，为后续流水线与 Scheduler 实现提供依据。明确区分**功能效果是什么**与**效果何时产生、何时可见**，不重复建立另一套指令功能语义。

同时提出初步的软件职责划分，区分周期推进、流水组件、调度控制和功能语义衔接，说明主要状态归属与交互边界。此处只形成设计方向，不提前固定具体 Go 类型、接口签名或文件组织。

## Markdown 与 YAML 分工

| 形式 | 负责内容 |
|---|---|
| **Markdown** | 抽象层级、组件职责、功能与时序边界、复杂行为说明、复用评估、证据解释及待决问题。 |
| **YAML** | 配置、流水节点、资源、通道、容量、延迟及规则关联等适合结构化查询和检查的条目。 |

二者共同构成 Timing IR，通过稳定标识相互引用，不将同一组参数或完整规则重复维护。具体字段和拆分方式根据分析需要确定，不要求建立通用、完备的 IR 语言。

沿用已有契约对事实、设计候选和未知事项的区分方式：有证据的结论保留来源，暂定抽象标为 `PROVISIONAL`，证据不足的事项标为 `UNRESOLVED`；后续实现与验证中持续更新。

## 本阶段边界与交付

在 `timing/` 下形成 Markdown 与 YAML 配合的初版 Timing IR，以及必要的来源、复用关系和待决事项说明。仅使用仓库内资料与已提供的依赖环境，不修改冻结 RTL，也不为适配时序设计改写已有功能语义。

本阶段不实现流水线执行器、Scheduler、cache 模型或 RTLSIM 对齐。解析与一致性检查可按实际需要补充，但不扩展为独立的通用工具工程。

## 完成标准

后续任务能够据此开始构建流水线，并识别调度控制与功能实现的衔接位置；结构化条目可解析、可追溯，未确认内容明确可见。

不以覆盖全部动态时序或达到周期精确作为本阶段要求。
